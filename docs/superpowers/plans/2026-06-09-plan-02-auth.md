# План 2 — Auth

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. For tasks marked **(TDD)** — use `superpowers:test-driven-development`.

**Goal:** Подключить Auth.js v5 с DB-сессиями, поднять таблицы `users` / `accounts` / `sessions` / `verification_tokens`, четыре OAuth-провайдера (Google, Yandex, VK, GitHub), флоу выбора `username` после первого логина, публичный профиль `/u/[username]` и middleware, которое заворачивает «безымянных» юзеров на `/welcome` и убивает сессию забаненных.

**Architecture:** `next-auth@beta` (v5) + `@auth/drizzle-adapter` поверх существующего `getDb()` (lazy pool из plan-01).

Конфиг Auth.js разделён на два модуля по официальному паттерну v5 (Edge-совместимость):
- **`src/lib/auth/config.edge.ts`** — провайдеры + callbacks + secret, **без** adapter и **без** обращения к `getDb()`. Безопасен для Edge runtime. Используется в `middleware.ts` для проверки сессии.
- **`src/lib/auth/config.node.ts`** — расширяет edge-конфиг `DrizzleAdapter(getDb())`. Импортируется только Node-роутами (`/api/auth/[...nextauth]`, server components через `auth()`).

Конфиг — функция-форма (`NextAuth(buildConfig)`), вычисляется при первом обращении: это нужно по той же причине, что lazy `getEnv()` / `getDb()` в plan-01 (`next build` импортирует все модули роутов, и eager-парс env роняет билд).

Провайдер VK — кастомный (Auth.js v5 не имеет builtin для VK ID), изолирован в одном файле. Сессии — DB-стратегия (мгновенный revoke по бану), TTL 30 дней. Каждый провайдер активен только при наличии своих `*_CLIENT_ID` + `*_CLIENT_SECRET` в `.env` — это даёт нишам форкаться без всех четырёх IdP.

**Tech Stack:** `next-auth@5.0.0-beta`, `@auth/drizzle-adapter`, `@auth/core` (тип `OAuthConfig` для VK), `ulid` (генерация `users.id`), Drizzle ORM 0.36, Postgres 16, Vitest, существующий tooling из plan-01.

**Спецификация:** [docs/superpowers/specs/2026-06-05-skelet-blog-design.md](../specs/2026-06-05-skelet-blog-design.md) — особенно §6.2, §6.3, §7 целиком.

**Definition of Done (что считается завершением плана 2):**
- `pnpm db:migrate` применяет миграцию с таблицами `users`, `accounts`, `sessions`, `verification_tokens` к локальному Postgres
- В Drizzle Studio (`pnpm db:studio`) видны 4 таблицы с правильными колонками и FK
- `pnpm test` зелёный (`username`-валидатор, VK profile-маппер, env с OAuth, schema-shape)
- `curl http://localhost:3000/api/auth/providers` отдаёт JSON с теми провайдерами, у которых заполнен secret в `.env` (на CI / в dev — пусто `{}`)
- Страницы `/login`, `/welcome`, `/u/[username]` доступны и SSR-рендерятся без ошибок (Lighthouse-checks не требуются)
- Header в авторизованном состоянии показывает аватар + dropdown с `/u/<my>` и «Выйти»; в неавторизованном — кнопку «Войти» через `<Link href="/login">` (маркер `TODO(plan-2)` снят)

- [ ] **Step 2.3: Заполнить `drizzle/schema.ts`**

**Важно про именование колонок в `accounts`:** TS-keys в этой таблице **намеренно** smal mixed-case (`userId`, `providerAccountId` — camelCase, но `refresh_token`, `access_token`, `expires_at`, `token_type`, `id_token`, `session_state` — snake_case). Это требование `@auth/drizzle-adapter`: он обращается к свойствам Drizzle-таблицы по тем именам, которые ожидает Auth.js core. Не «нормализуй» к одному стилю — адаптер сломается. Спека §6.2 даёт ровно эти имена, тест Step 2.1 проверяет именно их.

```ts
import {
  pgTable, text, varchar, integer, timestamp, pgEnum,
  index, primaryKey,
} from "drizzle-orm/pg-core";

export const userRole = pgEnum("user_role", ["user", "moderator", "admin"]);

export const users = pgTable("users", {
  id: text("id").primaryKey(),
  email: varchar("email", { length: 255 }).notNull().unique(),
  emailVerified: timestamp("email_verified"),
  username: varchar("username", { length: 20 }).unique(),
  name: varchar("name", { length: 100 }),
  image: text("image"),
  bio: text("bio"),
  role: userRole("role").notNull().default("user"),
  createdAt: timestamp("created_at").defaultNow().notNull(),
  bannedAt: timestamp("banned_at"),
}, (t) => ({
  usernameIdx: index("users_username_idx").on(t.username),
}));

export const accounts = pgTable("accounts", {
  userId: text("user_id").notNull().references(() => users.id, { onDelete: "cascade" }),
  type: text("type").notNull(),
  provider: text("provider").notNull(),
  providerAccountId: text("provider_account_id").notNull(),
  refresh_token: text("refresh_token"),
  access_token: text("access_token"),
  expires_at: integer("expires_at"),
  token_type: text("token_type"),
  scope: text("scope"),
  id_token: text("id_token"),
  session_state: text("session_state"),
}, (t) => ({
  pk: primaryKey({ columns: [t.provider, t.providerAccountId] }),
}));

export const sessions = pgTable("sessions", {
  sessionToken: text("session_token").primaryKey(),
  userId: text("user_id").notNull().references(() => users.id, { onDelete: "cascade" }),
  expires: timestamp("expires").notNull(),
});

export const verificationTokens = pgTable("verification_tokens", {
  identifier: text("identifier").notNull(),
  token: text("token").notNull(),
  expires: timestamp("expires").notNull(),
}, (t) => ({
  pk: primaryKey({ columns: [t.identifier, t.token] }),
}));
```

Имена snake_case в SQL (`provider_account_id`) и camelCase в TS (`providerAccountId`) — критично: `@auth/drizzle-adapter` именно так и ожидает (TS-property = его внутренний идентификатор, DB-column = что увидит Auth.js core, который ходит «по правилам Postgres»).

- [ ] **Step 4.3: Расширить `src/lib/env.ts`**

```ts
import { z } from "zod";

const schema = z.object({
  NODE_ENV: z.enum(["development", "test", "production"]).default("development"),
  DATABASE_URL: z.string().url().refine(s => s.startsWith("postgres://") || s.startsWith("postgresql://"), {
    message: "DATABASE_URL must be a Postgres connection string",
  }),
  NEXTAUTH_URL: z.string().url(),
  NEXTAUTH_SECRET: z.string().min(32, "NEXTAUTH_SECRET must be ≥32 chars"),

  GOOGLE_CLIENT_ID: z.string().min(1).optional(),
  GOOGLE_CLIENT_SECRET: z.string().min(1).optional(),
  YANDEX_CLIENT_ID: z.string().min(1).optional(),
  YANDEX_CLIENT_SECRET: z.string().min(1).optional(),
  VK_CLIENT_ID: z.string().min(1).optional(),
  VK_CLIENT_SECRET: z.string().min(1).optional(),
  GITHUB_CLIENT_ID: z.string().min(1).optional(),
  GITHUB_CLIENT_SECRET: z.string().min(1).optional(),
}).superRefine((v, ctx) => {
  for (const p of ["GOOGLE", "YANDEX", "VK", "GITHUB"] as const) {
    const id = (v as Record<string, string | undefined>)[`${p}_CLIENT_ID`];
    const sec = (v as Record<string, string | undefined>)[`${p}_CLIENT_SECRET`];
    if (!!id !== !!sec) {
      ctx.addIssue({
        code: z.ZodIssueCode.custom,
        path: [`${p}_CLIENT_SECRET`],
        message: `${p}_CLIENT_ID and ${p}_CLIENT_SECRET must be set together`,
      });
    }
  }
});

export type Env = z.infer<typeof schema>;

export function parseEnv(input: Record<string, string | undefined>): Env {
  const result = schema.safeParse(input);
  if (!result.success) {
    throw new Error("Invalid env: " + result.error.issues.map(i => `${i.path.join(".")}: ${i.message}`).join("; "));
  }
  return result.data;
}

let cached: Env | null = null;
export function getEnv(): Env {
  if (cached) return cached;
  cached = parseEnv(process.env);
  return cached;
}
```

Один `superRefine` на всю схему — проще читается, чем merge-нутые object-схемы (там TS-вывод полей теряется).

export const RESERVED_USERNAMES = [
  "admin", "administrator", "root", "moderator", "mod",
  "api", "auth", "login", "logout", "welcome", "settings",
  "new", "edit", "p", "u", "t", "tag", "tags",
  "about", "rules", "contacts", "help", "support",
  "null", "undefined", "system", "skelet",
] as const;

const FORMAT = /^[a-z0-9_-]{3,20}$/;

export type UsernameValidation =
  | { ok: true }
  | { ok: false; reason: "format" | "reserved" };

export function validateUsername(input: string): UsernameValidation {
  if (!FORMAT.test(input)) return { ok: false, reason: "format" };
  if ((RESERVED_USERNAMES as readonly string[]).includes(input)) return { ok: false, reason: "reserved" };
  return { ok: true };
}

import Google from "next-auth/providers/google";
import Yandex from "next-auth/providers/yandex";
import GitHub from "next-auth/providers/github";

export function buildEdgeConfig(): NextAuthConfig {
  const env = getEnv();
  const providers: NextAuthConfig["providers"] = [];

  if (env.GOOGLE_CLIENT_ID && env.GOOGLE_CLIENT_SECRET) {
    providers.push(Google({ clientId: env.GOOGLE_CLIENT_ID, clientSecret: env.GOOGLE_CLIENT_SECRET }));

    providers.push(GitHub({ clientId: env.GITHUB_CLIENT_ID, clientSecret: env.GITHUB_CLIENT_SECRET }));
  }

  return {
    providers,
    session: { strategy: "database", maxAge: 30 * 24 * 60 * 60 },
    secret: env.NEXTAUTH_SECRET,
    pages: { signIn: "/login" },
    callbacks: {
      session({ session, user }) {

## Task 10: `/welcome` — выбор username (Server Action)

Сервер-экшен `setUsername`: проверяет валидатор (Task 5), проверяет уникальность по БД, апдейтит `users.username`, редиректит на `/`.

- [ ] **Step 10.1: Server Action `src/app/(auth)/welcome/actions.ts`**

Action сам редиректит и в success-, и в error-кейсах. Страница не делает `try/catch` — просто `<form action={setUsername}>`. Ошибки прокидываем через `searchParams` (`?err=format|reserved|taken`).

```ts
"use server";
import { redirect } from "next/navigation";
import { eq } from "drizzle-orm";
import { auth } from "@/lib/auth";
import { getDb } from "@/lib/db";
import { users } from "@db/schema";
import { validateUsername } from "@/lib/auth/username";

export async function setUsername(formData: FormData): Promise<void> {
  const session = await auth();
  if (!session?.user?.id) redirect("/login");

  const raw = String(formData.get("username") ?? "").trim().toLowerCase();
  const validation = validateUsername(raw);
  if (!validation.ok) redirect(`/welcome?err=${validation.reason}`);

  const db = getDb();
  const existing = await db
    .select({ id: users.id })
    .from(users)
    .where(eq(users.username, raw));

  if (existing.length > 0 && existing[0].id !== session.user.id) {
    redirect("/welcome?err=taken");
  }

  await db.update(users).set({ username: raw }).where(eq(users.id, session.user.id));
  redirect("/");
}
```

`redirect()` в Next 15 бросает специальный exception, поэтому ранние возвраты не нужны — TS видит цепочку как never-returning.

export default async function UserProfilePage({

## Task 12: Middleware — username-redirect и ban-kill

В middleware импортируем **edge**-вариант auth (`@/lib/auth.edge`) — он без adapter, не тянет `pg` и совместим с Edge runtime. Сессия читается из cookie, поля `username` / `bannedAt` уже подмешаны в её payload через `callbacks.session` (Step 7.2).

**Files:**
- Create: `src/middleware.ts`

- [ ] **Step 12.1: Middleware**

```ts
import { auth } from "@/lib/auth.edge";
import { NextResponse } from "next/server";

const PUBLIC_PREFIXES = ["/login", "/api", "/u/", "/_next", "/favicon", "/icons", "/manifest"];

// TODO(plan-3+): rate-limit на /api/auth/callback/* (спека §7.6). В V1 пропускаем —
// полагаемся на friction OAuth; если поедет спам в проде, добавим in-memory IP-счётчик
// здесь (фаза 3 — Redis).
// TODO(plan-5): admin-role gating для /admin/* (спека §7.5). Когда появится /admin —
// проверять session.user.role === "admin", иначе редирект на /.

export default auth((req) => {
  const { pathname } = req.nextUrl;
  const session = req.auth;

  // Не-авторизованных — не трогаем (пусть страницы решают сами)
  if (!session?.user) return NextResponse.next();

  // Забаненный юзер: выкидываем cookie (вид сессии Auth.js v5 — обнуляем next-auth.session-token)
  if (session.user.bannedAt) {
    const url = req.nextUrl.clone();
    url.pathname = "/";
    const res = NextResponse.redirect(url);
    for (const name of ["authjs.session-token", "__Secure-authjs.session-token"]) {
      res.cookies.set(name, "", { maxAge: 0, path: "/" });
    }
    return res;
  }

  // Авторизованный, но без username — гоним на /welcome (кроме самого /welcome и публичных префиксов)
  if (!session.user.username) {
    if (pathname === "/welcome") return NextResponse.next();
    if (PUBLIC_PREFIXES.some(p => pathname === p || pathname.startsWith(p))) return NextResponse.next();
    const url = req.nextUrl.clone();
    url.pathname = "/welcome";
    return NextResponse.redirect(url);
  }

  return NextResponse.next();
});

export const config = {
  matcher: [
    // Все маршруты, кроме статики и API-внутренностей Next
    "/((?!_next/static|_next/image|favicon.ico|icons/.*|manifest\\.webmanifest).*)",
  ],
};
```

**Edge-совместимость:** благодаря split-конфигу из Task 7, `auth` из `auth.edge.ts` не тянет `pg` (нет `DrizzleAdapter`). Middleware видит только `session.user.{id,username,role,bannedAt}` — поля, прокинутые в `callbacks.session`. SQL-запросы делаются только в server components / API через node-`auth()`.

Если этот шаг всё-таки валится с `Can't resolve 'pg'`/`dns`/`net` — значит, в edge-config случайно затащен модуль, импортирующий БД. Проверь, что `src/lib/auth/config.edge.ts` **не импортит** `@/lib/db` или `@db/schema`.

## Реализация: расхождения с планом (заполнено по факту, 2026-06-09)

1. **`@auth/core` версия (Task 6/7).** План фиксировал `@auth/core@^0.34.3`, но `next-auth@5.0.0-beta.31` тащит `@auth/core@0.41.2`. Две параллельные версии в `node_modules` ломали `pnpm build` на `OAuthConfig` (типы из разных копий). Поднял до `^0.41.2`.
2. **`User` interface (Step 7.1).** План делал `username/role/bannedAt` обязательными в `interface User`. Это конфликтует с `profile()`-маппером любого OAuth-провайдера (`{id,name,email,image}`), build падает. Поля сделаны опциональными в `User`, но остались обязательными в `Session.user` — последние заполняются из DB-row в session callback (`?? null` / `?? "user"`). Канонический паттерн next-auth, план в этой части просто промазал.
3. **Порядок проверок в `validateUsername` (Task 5).** План проверял `format` перед `reserved`. В `RESERVED_USERNAMES` есть однобуквенные `u`, `t`, `p` (это будущие реальные роуты `/u/`, `/t/`, `/p/`), они режутся регексом `^[a-z0-9_-]{3,20}$` раньше, чем доходят до reserved-листа, и тест плана падал. Перевернул порядок: `reserved → format`. Однобуквенные слова всё равно должны блокироваться, потому что это занятые префиксы маршрутов.
4. **`.env.example` (новый коммит, не входил в план).** План оставлял шаблон с пустыми значениями `GOOGLE_CLIENT_ID=` и т.п. Zod `.string().min(1).optional()` интерпретирует пустую строку как присутствующее значение и валит первый же `pnpm dev`. Все опциональные ключи (`OAuth`, `R2`, `BACKUP`, `INDEXNOW_KEY`, `YANDEX_METRIKA_ID`) закомментированы префиксом `#`, локальный `.env` приведён в то же состояние. Это фикс на уровне источника, а не «преобразование пустых в `undefined`» в env-схеме — последнее было бы мусорным обходом.
5. **`auth.edge.ts` — eager-конфиг (Task 12).** План передавал в `NextAuth` функцию-форму (`NextAuth(buildEdgeConfig)`) и в edge-, и в node-инстансе. Eager-форма не нужна для node — там lazy спасает `next build` от eager-парсинга env. Но в edge lazy-форма ломает middleware-wrapper: в `node_modules/next-auth/lib/index.js` ветка `typeof config === "function"` оборачивает `auth(handler)` во внешний `async`, и возвращается `Promise<fn>` вместо функции. Next dev падает: «Middleware must export a `middleware` or a `default` function». Сделал eager только в `auth.edge.ts` (`NextAuth(buildEdgeConfig())`). В `auth.ts` (node) lazy сохранил — он защищает `next build` от вычитывания env при сборке route-handler-ов. Комментарий с объяснением — в `src/lib/auth.edge.ts`.

9. **VK ID — кастомный OAuth-роут вместо NextAuth-провайдера.** План §14 + `src/lib/auth/providers/vk.ts` использовали стандартный путь `next-auth/providers/...` через `callback.js` → `oauth4webapi`. Это не взлетело по трём причинам:
   - VK ID требует `device_id` (приходит query-параметром в callback) в **body** token-exchange, а `@auth/core@0.41.2` его туда не докладывает.
   - `OAuthConfig.token.request` объявлен в `oauth.d.ts` но в `callback.js` не вызывается — единственная точка расширения через `[customFetch]`-symbol.
   - VK ID режет точки из JWE-state Auth.js → `OperationProcessingError: unexpected "state" response parameter value`.
   
   Поэтому VK вынесен в собственную пару Node-роутов: [/api/oauth/vk/start](src/app/api/oauth/vk/start/route.ts) (PKCE+state в HttpOnly-куках, редирект на `https://id.vk.com/authorize`) и [/api/oauth/vk/callback](src/app/api/oauth/vk/callback/route.ts) (валидация state, POST-form token exchange с `device_id`, POST-form user_info). Хелпер [src/lib/auth/oauth-vk.ts](src/lib/auth/oauth-vk.ts) делает upsert в `users`/`accounts` и пишет строку в `sessions` напрямую через Drizzle. Куки сессии (`authjs.session-token` / `__Secure-authjs.session-token`) совпадают с NextAuth-форматом — `await auth()` подхватывает сессию как родную, остальной код (`session` callback, middleware, `/welcome`) не меняется. Старый файл `providers/vk.ts` и `tests/auth/vk-provider.test.ts` удалены; добавлены `tests/auth/oauth-vk.test.ts` (6 кейсов: PKCE-инвариант, state без точек, sub-provider guard, cookie-name, authorize URL). Для тестов в `env.ts` экспортирован `_resetEnvCacheForTests()`.
   
   **Инфра-требование:** VK ID не принимает custom-порты в Trusted Redirect URL — только 80/443. Для локальной разработки с VK нужен Caddy reverse-proxy `:80 → :3000` (`sudo caddy reverse-proxy --from :80 --to :3000`) и `NEXTAUTH_URL=http://localhost` (без порта). Без Caddy остаётся только Яндекс — тогда `NEXTAUTH_URL=http://localhost:3000` и Redirect URI в кабинете Яндекса с `:3000`.
